# Flow Versioning Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a user save named snapshots of a flow's graph and restore any of them — roadmap item #9 of the Flow gap analysis (`ARCHITECTURE.md` §9.2).

**Architecture:** A new table `flow_versions` (migration `024_flow_versions.sql` + `.pg.sql`) holds immutable snapshots of a flow's `nodes_json`/`edges_json`. New endpoints under `/flows/{id}/versions` list, create, read and restore versions; restore first auto-snapshots the current graph (so it is undoable) and respects the Phase #3 validation gate when the flow is active. The dashboard adds a "Versions" drawer on the canvas (save with optional label, list, restore). No new dependency, no Octop patch; one new migration (additive only — it creates a table and bumps `_schema_version`, so existing data is untouched).

**Tech Stack:** Python 3.12 / FastAPI / SQLite+Postgres SQL / pytest (backend); React + antd + vitest (dashboard).

**Spec:** `customize/docs/design-flow.md` §6 (data model), §7 (API), §9 (frontend); `ARCHITECTURE.md` §9.2 item 9. Task 1 and Task 2 each add the matching doc paragraph.

  - `GET /flows/{flow_id}/versions` ⇒ list of the same summary shape, newest first (`version_no` desc); no graphs.
  - `GET /flows/{flow_id}/versions/{version_no}` ⇒ summary plus `"nodes"` and `"edges"` (parsed JSON); unknown number ⇒ 404.
  - `POST /flows/{flow_id}/versions/{version_no}/restore` ⇒ `200` `{"flow": <same payload as GET /flows/{id}>, "restored_from": <version_no>, "backup_version_no": <int>}`. Unknown number ⇒ 404. If the flow's status is `active` and the version's graph has validation **errors** (Phase #3 `validate_graph`/`has_errors`, same coercion path `_to_engine_graph`) ⇒ `422` with detail string `"restored version has N validation error(s): <first error message>; deactivate the flow first or pick another version"` and **nothing changes** (no backup, no overwrite). Otherwise, in one transaction: insert an `auto` version of the current graph with label `Before restore to v<N>`, then overwrite `nodes_json`/`edges_json`/`updated_at` of the flow (status, name, description untouched). The cap rule applies to the auto backup too.
  - `delete_flow` also deletes the flow's versions explicitly (before deleting `flows`), same discipline as runs.

## Review Focus

- Migration applies on a fresh DB **and** on an existing v23 DB (additive): a test (or the sandbox DB bootstrapping path the other tests use) shows `flow_versions` exists and `_schema_version` is 24; no existing flow/run row is altered. Task 1.
- Restore into an **active** flow with an invalid version is refused with 422 and leaves the graph, status, version list (no backup row) untouched; into a draft flow the same restore succeeds. Task 1 `test_restore_invalid_version_into_active_flow_is_rejected_unchanged`, `test_restore_into_draft_allows_invalid_version`.
- Restore is undoable: restoring v1 then restoring `backup_version_no` returns the pre-restore graph exactly. Task 1.
- Version numbers are never reused: after the cap deletes old rows or after deleting nothing, the next number is still `MAX+1`; 55 creates leave exactly 50 rows with numbers 6..55. Task 1.
- Isolation: another user's flow ⇒ 403/NOT_FOUND on every versions route, and a `version_no` from flow A addressed through flow B ⇒ 404 (no cross-flow leak). Task 1.
- Deleting a flow removes its versions (no orphan rows). Task 1.
- Dashboard: a restore failure keeps the drawer open with an error and does not reload the canvas; a successful restore reloads the canvas graph/name/status; "Save version" saves the canvas first and does not create a version if the save fails; double-clicking Restore or Save version sends one request. Task 2.
